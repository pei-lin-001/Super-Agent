## 账本与评测错误

模型预检各一次成功，不含研究材料。已返回 usage 的调用如下；单位为 token，缓存读取单列，不能据此推算实际费用：

| 阶段 | 实际完成调用 | 非缓存输入 | 缓存读取 | 输出 |
|---|---:|---:|---:|---:|
| Flash 与 Sol 预检 | 2 | 46 | 0 | 17 |
| 基线：Flash | 27 | 263,446 | 1,007,872 | 37,281 |
| 基线：Sol | 8 | 75,940 | 370,432 | 6,551 |
| 修改后：Flash | 14 | 123,808 | 277,376 | 9,341 |
| 修正驱动 new-c-v2：Flash | 36 | 299,332 | 817,152 | 20,068 |
| 合计 | 87 | 762,572 | 2,472,832 | 73,258 |

驱动账本记载共 89 次“sent”，但它在进入模型适配器前就计数，所以这是准入逻辑调用数，其中 87 次 HTTP 成功且返回 usage。两次被取消的逻辑调用在各自 `model_call` 中均记录 `http_attempts=0`；冻结源码中适配器在并发闸门后先检查取消信号，再增加 HTTP 尝试数并发起请求，故这两次没有发送 HTTP 请求，没有相应提供方 token 消耗。修改后组还出现一次未进入适配器的预算拒绝，数据库将它记录为 failed，但它不在 89 次 sent 中。日志里原先将两次取消计为 usage 未知，是驱动的保守误记；未生成的模型回答无法恢复。

预算门控把当前不满足并发或 token 预留的情况直接抛成业务模型异常，触发任务失败并取消另一个调用；基线旧版驱动达到调用上限即停止，也没有等最后一个逻辑调用完成。这破坏了对照。本轮没有任何额外业务消息干预；修正驱动后的追加运行仅限 new-c-v2，没有扩大组别或重跑基线。

针对上述驱动缺陷，修正驱动采取的方案是：门控将临时资源不足的调用排队，等已有调用结算后重算；达到不可继续的观察边界时只停止发新请求，等待已获准请求及其工具结果落库，再记录独立的 `experimentStopped` 和停止前业务状态；关闭运行时造成的取消必须单独标注。分别记录逻辑调用和实际 HTTP 尝试，并用模拟模型验证上述末次提交和预算排队场景；真实提供方错误和所有并发情形未因此得到完整验证。原始一次性驱动、各次源码快照、数据库、任务材料及账本保存在 `/private/tmp/sa-collab-20261113/`，可能被系统清理；未将研究原件、临时驱动或密钥提交仓库。基线和修改后实际驱动 SHA-256 分别为 `e5be9f54584db03e1fb599d52f1d01f216e9bfd7d6c748c97a53538fc4cf937d`、`380af4561855d892761bb6cff0a22504bb206cfe1dde6a8016de9648d3cfa67a`，两版在停止边界处理上不同。
